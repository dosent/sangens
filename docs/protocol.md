# Протокол Sangens: восстановленные данные

Источник — предоставленный владельцем APK React Native/Hermes и декомпиляция. Протокол восстановлен по коду приложения; вход и чтение состояния подтверждены авторизованным ответом действующего сервиса. Управляющие запросы пока не проверялись. Адрес: `https://api.sangens.com/api`.

## Вход

Приложение отправляет `POST /email/send` с `email` и `recaptcha`, получает `data.emailToken`; проверяет код через `POST /email/check`, затем выполняет `POST /auth/loginByEmail` с `token` и `code`. Итог — `data.token`, используемый как `Authorization: Bearer …`. Внешний ответ обёрнут в `data`.

`refreshToken` в найденном компоненте относится к обновлению CAPTCHA, а не облачного токена. Подтверждённого API продления авторизации нет.

## Проверка входа на действующем сервисе 27 октября 2026

Выполнены только пустые запросы без почты и кода; писем и команд печи они не отправляют:

1. Без служебных заголовков: HTTP 422, `Device Id header is invalid`.
2. С новым собственным идентификатором HA и `App-Platform: homeassistant`: HTTP 422, `Platform header is invalid`.
3. С полем платформы мобильного протокола `android`: HTTP 422, ошибка обязательного `email`; ошибки `recaptcha` в этом ответе нет.

Код приложения задаёт `App-DeviceId`, `App-Platform`, `App-Version`, `App-Lang`. Клиент HA создаёт свой идентификатор и сохраняет его на сервере. Идентификатор телефона не копируется. User-Agent явно обозначает `HomeAssistant-Sangens`, поле платформы используется для совместимости с протоколом.

При ручной проверке версии 0.2.1 сервис действительно запросил CAPTCHA. Это отдельный шаг приложения: WebView загружает локальный HTML с baseURL `https://api.sangens.com/`, скриптом Google и публичным site key. После `grecaptcha.ready()` выполняется `grecaptcha.execute(siteKey)` без параметра action. Результат передаётся в React Native и затем в `recaptcha` запроса почты. Страница браузерного входа не найдена, корень API перенаправляет на административный вход и не используется.

Версия 0.3.0 воспроизводит этот механизм в разовом помощнике macOS WKWebView с тем же baseURL и публичным site key. Отличие: выполнение начинается только кнопкой человека; результат переносится вручную в поле HA. Google выдаёт настоящий короткоживущий результат; принятие его Sangens подтверждено ручным входом владельца. Не подменяются результат проверки, идентификатор установленного приложения, TLS или User-Agent. Секретного ключа reCAPTCHA у интеграции нет; проверку результата выполняет Sangens.

По [документации Google](https://developers.google.com/recaptcha/docs/verify) результат одноразовый и действует две минуты. Помощник хранит его в памяти не более 110 секунд, не записывает на диск и очищает собственную запись в буфере обмена, если пользователь ещё не заменил её. HA держит только отпечатки уже использованных результатов в незавершённом потоке и не включает их в постоянную запись настройки.

Поток: `/email/send` возвращает `emailToken`; `/email/check` с тем же `emailToken` и кодом возвращает `isNeedRegister`. Для существующего аккаунта `/auth/loginByEmail` получает исходный `emailToken` в поле `token` и тот же код. Регистрация автоматически не выполняется.

Между письмами — минимум 60 секунд. После трёх неверных кодов или двух неудачных отправок с CAPTCHA — минимум 5 минут; на HTTP 429 соблюдается более длинный `Retry-After`. Параллельные нажатия не ставятся в очередь. После успешного входа ошибка чтения устройств повторяет только GET, без нового письма и входа.

Проверка настоящей почты, кода и чтения устройства выполнена владельцем 27 октября: общая запись создана, GET состояния возвращает HTTP 200. Отсутствие поля CAPTCHA в ответе на пустой запрос не доказывает успешный вход. Ручная проверка в HA выполняется пользователем; код не передаётся в чат. Сессия сохраняется в общей записи на сервере, краткоживущие данные и код не сохраняются.

## Запросы

| Операция | Запрос | Тело |
| --- | --- | --- |
| Устройства | GET `/microchip-user` | — |
| Состояние | GET `/microchip-user/{binding_id}` | — |
| Питание | POST `/microchips/{microchip_id}/set-remote-control-status` | `remoteControlStatus`: `ON` или `off` |
| Воздух | POST `/microchips/{microchip_id}/set-air-temperature` | `setAirTemperature` |
| Камни | POST `/microchips/{microchip_id}/set-target-stone-temperature` | `targetStoneTemperature` |
| Режим | POST `/microchip-user/{binding_id}/set-mode` | `modeId` |

В `DeviceService` список извлекается как `response.data.data` и десериализуется фабрикой моделей. Точную форму списка и сведения о пагинации требуется сверить на действующем аккаунте, прежде чем считать совместимость подтверждённой.

`binding_id` — идентификатор пользовательской привязки; `microchip_id` — идентификатор контроллера в `microchip.id`. Они не взаимозаменяемы. Команда питания не должна использовать переключение: точные значения чувствительны к регистру.

## Показания

`microchip.connectionStatus`: `online` / `offline`. `microchip.data.remoteControlStatus`: `ON` / `off`. Температуры: `currentAirTemperature`, `setAirTemperature`, `firstStoneTemperature`, `secondStoneTemperature`, `targetStoneTemperature`. Нагреватели: `airHeaterStatus`, `firstStoneHeaterStatus`, `secondStoneHeaterStatus`; допустимые значения этих признаков ещё требуют проверки. Неизвестный формат не считается выключением.

Режимы: `mode`, `defaultMode`; ограничения в данных режима: `minAirTemp`, `maxAirTemp`, `minHeaterTemp`, `maxHeaterTemp`. Подробную вложенность необходимо проверить. Нельзя брать диапазоны со шкалы экрана в качестве допустимых границ команд.

Ответ 409 обозначает ожидание другой команды (`WAIT_ACTION_ERROR_CODE` в приложении). Не выполнять автоматический повтор управляющего запроса. Тайм-аут означает неизвестный результат, а не гарантированный отказ.

## Уровень проверки

- Чтение APK: выполнено.
- Совпадение с работающим аккаунтом: не проверено.
- Ручной вход из HA: реализован и проверен на искусственном сервисе; настоящее письмо и код требуют проверки пользователем.
- Команды реальной печи: не выполнялись.
